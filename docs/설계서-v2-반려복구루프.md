§7의 1~4단계를 구현했다. 5단계 이후는 실제 운영 필요가 생길 때까지 미룬다.

| 단계 | 상태 | 위치 |
|---|---|---|
| 1. Ads API 읽기 어댑터 | ✅ **어댑터 경계까지** | `ads/client.py` |
| 2. normalizer + 미매핑 원장 | ✅ | `ads/mapping.py` |
| 3. 재점검 + 재현율 측정 | ✅ | `ads/recheck.py` |
| 4. 원장 + 리포트 | ✅ | `ads/report.py`, `ads/models.py` |
| 5. remediator (수정안) | ⬜ 미착수 | — |
| 6. 승인 UI | ⬜ 미착수 | — |
| 7. resubmitter + 안전장치 | ⚠️ **안전장치만 앞당겨 구현** | `ads/watcher.py` |
| 8. remediator (LLM) | ⬜ 미착수 | — |

`python -m adpolicy.ads` 로 전 구간이 픽스처만으로 돈다. 테스트 `tests/test_ads_pipeline.py` 25건.

### 설계서와 달라진 점 세 가지

구현하면서 판단이 바뀐 부분을 숨기지 않고 적는다.

**① 재점검이 `/v1/check`를 직접 부르지 않는다 (§3-3 수정)**

설계서에는 "v1의 `/v1/check`를 그대로 호출한다"고 썼는데, 그렇게 하면 이 모듈을 테스트할 수 없고 채점 결과가 실행할 때마다 달라진다. 네트워크와 LLM이 끼기 때문이다. 그래서 **`PageChecker`를 주입받는 구조**로 바꿨다.

```python
class PageChecker(Protocol):
    def __call__(self, *, url, ad_copy, headlines, descriptions) -> set[str]: ...
```

운영에서는 v1 파이프라인을, 테스트·재현에서는 저장된 HTML을 쓰는 구현(`make_offline_checker`)을 꽂는다. 후자는 평가 하네스와 **같은 계층**을 쓴다 — 두 곳이 다른 판정을 내면 숫자를 비교할 수 없다.

**② 안전장치를 7단계에서 앞으로 당겼다 (§5)**

원래 순서대로라면 재제출(7단계)과 함께 만들 것들이었다. 그런데 1단계만 만들어도 "정지된 계정의 소재를 읽는" 일이 벌어질 수 있다. **잘못된 대상을 큐에 넣는 것이 이 시스템에서 가장 위험한 실수**이므로, 읽기만 하는 지금 단계에서 이미 막아 두었다.

- 계정이 `ENABLED`가 아니면 **소재를 읽지도 않고** `AccountHalted`로 중단
- `SeenIndex`를 **(소재, 사유) 단위**로 — 소재 단위로 하면 하나를 고친 뒤 다른 사유로 반려됐을 때 놓친다

**③ `GoogleAdsClient`를 일부러 구현하지 않았다 (§8-1과 연결)**

스키마를 실제 응답으로 검증하지 못한 상태에서 실제 호출을 흉내 내면, 필드명 추측이 파이프라인 전체로 번진다. 그래서 호출하면 `NotImplementedError`로 "응답을 덤프해 스키마를 교정한 뒤 구현하라"고 거부한다. 테스트가 이 거부를 강제한다.

## 0. 이 문서의 범위

### 만드는 것

광고 소재가 **반려(disapproved)되었을 때**, 사유를 자동으로 수집해 원인을 특정하고, 수정 지점을 증거와 함께 제시한 뒤, 사람이 승인하면 재제출하고, **승인 여부를 되먹여 사전 점검의 정확도를 올리는** 루프.

### 만들지 않는 것 (명시적 제외)

- **정지된 계정을 대체할 새 계정 생성** — Google Ads 시스템 우회 정책 위반
- **동일 도메인·결제수단의 다른 계정 이전**
- **사람 확인 없는 무제한 자동 재제출** — 심사 시스템에 대한 부하이자 우회로 간주될 수 있음

이 세 가지는 기술적 난이도 문제가 아니라 **설계 원칙으로 배제**한다. v1이 `ABUSE-PARAM-CLOAKING`을 계정 정지 등급으로 분류하는 도구인 이상, v2가 우회 도구가 되는 것은 자기모순이다.

### 한 줄 요약

> v1은 **제출 전**에 막고, v2는 **반려된 뒤**에 고친다. 그리고 v2의 결과가 v1을 더 정확하게 만든다.

## 1. 왜 만드는가

### 1-1. v1의 구조적 공백

v1은 "이 페이지와 문구가 정책에 걸릴 것 같다"를 예측한다. 그런데 **예측이 맞았는지 틀렸는지 확인할 방법이 없다.** 실제로 제출했을 때 Google이 어떻게 판정했는지가 시스템 밖에 있기 때문이다.

이것이 v1의 가장 큰 약점이다. README에 "PaddleOCR 정확도는 측정하지 않았다"고 적은 것과 같은 종류의 공백이 판정 전반에 존재한다.

### 1-2. 반려 사유는 API로 읽을 수 있다

Google Ads API는 소재별 정책 판정 결과를 구조화된 형태로 제공한다. 즉 **정답 레이블을 공짜로 얻을 수 있다.**

```
ad_group_ad.policy_summary.approval_status      # 승인 여부
ad_group_ad.policy_summary.review_status        # 심사 진행 상태
ad_group_ad.policy_summary.policy_topic_entries # 위반 사유 목록
  ├─ topic          # 예: "DESTINATION_NOT_WORKING"
  ├─ type           # PROHIBITED / LIMITED / FULLY_LIMITED / ...
  ├─ evidences[]    # 근거 (텍스트 조각, URL, HTTP 코드 등)
  └─ constraints[]  # 제한 내용 (국가/지역 등)
```

Google이 공식 샘플 코드 `Get all disapproved ads`를 제공한다.

⚠️ **미확인**: `type` enum의 정확한 값 목록과 `evidences` 하위 구조는 API 버전에 따라 달라진다. 구현 전에 사용할 API 버전의 레퍼런스를 직접 확인해야 한다. 이 문서의 필드명은 설계 논의를 위한 것이며 검증된 값이 아니다.

### 1-3. 이것이 플라이휠이다

```
사전 점검 → 제출 → 판정 → 사유 수집 → 수정 → 재제출 → 판정
                              ↓
                     "무엇이 실제로 걸렸나" 축적
                              ↓
                     사전 점검 규칙 보정 ──┐
                              ↑            │
                              └────────────┘
```

쓰면 쓸수록 정확해지는 구조. 에어스메디컬 공고의 "Flywheel 엔진"이 말하는 것의 구체적 사례.

## 2. 전체 파이프라인

```
                         ┌──────────────────────────┐
                         │  Google Ads API          │
                         │  (읽기 전용 + 소재 수정)  │
                         └───────────┬──────────────┘
                                     │ GAQL 폴링
                                     ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [1] watcher — 반려 감지                                   │
  │     approval_status != APPROVED 인 소재를 큐에 적재        │
  │     신규 반려만 (이미 처리한 건 change_status로 필터)      │
  └───────────────────────────┬──────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [2] normalizer — 사유 정규화                              │
  │     Google policy topic  →  내부 rule id 매핑             │
  │     매핑 실패 시 unmapped 로 격리 (버리지 않는다)          │
  └───────────────────────────┬──────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [3] re-check — 재점검                                     │
  │     v1의 /v1/check 를 그대로 호출                          │
  │     단, Google이 지목한 rule 을 우선순위로 올려서           │
  │     → "우리도 잡았나 / 못 잡았나" 를 기록                  │
  └───────────────────────────┬──────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [4] remediator — 수정안 생성                              │
  │     rule id 별 수정 전략 + LLM 제안                        │
  │     반드시 evidence 를 붙인다 (v1의 verify_evidence 재사용)│
  └───────────────────────────┬──────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [5] approval gate — 사람 승인  ★ 필수                     │
  │     수정안을 보여주고 승인/거부/직접수정 을 받는다          │
  │     자동 통과 경로 없음                                    │
  └───────────────────────────┬──────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [6] resubmitter — 재제출                                  │
  │     소재 수정 후 재등록 → 심사 재진입                      │
  │     재시도 횟수 상한 / 쿨다운 강제                         │
  └───────────────────────────┬──────────────────────────────┘
                              ▼
  ┌──────────────────────────────────────────────────────────┐
  │ [7] ledger — 결과 기록 (플라이휠 원장)                     │
  │     (사유, 수정 내용, 재심사 결과) 3튜플 저장              │
  │     → 규칙 정확도 리포트 / 수정 전략 승률                  │
  └──────────────────────────────────────────────────────────┘
```

v1의 `check-history` 원장 구조를 [7]에 그대로 확장한다.

## 3. 컴포넌트 상세

### 3-1. watcher — 반려 감지

**책임**: 새로 반려된 소재만 골라 큐에 넣는다.

```python
# api/src/adpolicy/ads/watcher.py

GAQL = """
SELECT
  ad_group_ad.ad.id,
  ad_group_ad.ad.final_urls,
  ad_group_ad.ad.responsive_search_ad.headlines,
  ad_group_ad.ad.responsive_search_ad.descriptions,
  ad_group_ad.policy_summary.approval_status,
  ad_group_ad.policy_summary.review_status,
  ad_group_ad.policy_summary.policy_topic_entries,
  ad_group.id, campaign.id
FROM ad_group_ad
WHERE ad_group_ad.policy_summary.approval_status IN ('DISAPPROVED', 'AREA_OF_INTEREST_ONLY')
  AND ad_group_ad.status != 'REMOVED'
"""
```

**설계 판단**

| 판단 | 이유 |
|---|---|
| 폴링 주기 **1시간** | 심사는 보통 1영업일 단위로 움직인다. 분 단위 폴링은 API 쿼터만 소모 |
| `APPROVED_LIMITED`도 수집하되 **처리는 안 함** | "제한 승인"은 반려가 아니다. 하지만 무엇이 제한되는지는 학습 데이터로 값지다 |
| 이미 본 (ad_id, policy_topic) 조합은 **스킵** | 같은 사유로 반복 트리거되면 재제출 루프에 빠진다 |
| 계정 상태도 함께 확인 (`customer.status`) | 계정 자체가 SUSPENDED면 소재 수정은 무의미하다. **즉시 중단하고 사람에게 알린다** |

마지막 항목이 중요하다. **계정 정지는 이 시스템이 다루는 문제가 아니다.** 감지하면 멈추고 사람에게 넘긴다.

### 3-2. normalizer — 사유 정규화

**책임**: Google의 policy topic 문자열을 v1의 내부 rule id로 매핑한다.

이것이 **이 프로젝트에서 가장 어려운 부분**이다. 양쪽 어휘가 다르고, Google의 topic 목록은 공개된 전체 명세가 없으며, 시간이 지나면 바뀐다.

```python
# api/src/adpolicy/ads/mapping.py

TOPIC_TO_RULE: dict[str, list[str]] = {
    "DESTINATION_NOT_WORKING":        ["DEST-UNREACHABLE"],
    "DESTINATION_MISMATCH":           ["DEST-MISMATCH"],
    "MALICIOUS_OR_UNWANTED_SOFTWARE": ["ABUSE-MALWARE"],
    "CLOAKING":                       ["ABUSE-CLOAKING",
                                       "ABUSE-PARAM-CLOAKING"],
    "TRICK_TO_CLICK":                 ["MIS-CLICKBAIT"],
    "UNACCEPTABLE_BUSINESS_PRACTICE": ["MIS-BUSINESS-IDENTITY"],
    "PERSONALIZED_ADVERTISING":       ["KR-CONSENT-MISSING"],
    # ... 확인된 것만 추가한다. 추측으로 채우지 않는다.
}
```

**설계 원칙 — 매핑 실패를 숨기지 않는다**

```python
def normalize(topic: str) -> Mapping:
    rules = TOPIC_TO_RULE.get(topic)
    if rules is None:
        # 버리지 않는다. 격리해서 쌓고, 주기적으로 사람이 본다.
        record_unmapped(topic)
        return Mapping(rules=[], status="unmapped")
    return Mapping(rules=rules, status="mapped")
```

`unmapped` 원장은 **이 시스템의 가장 값진 산출물 중 하나**다. "Google은 반려했는데 우리 규칙에는 대응물이 없다" = v1에 빠진 규칙의 목록이기 때문이다.

| 상태 | 의미 | 조치 |
|---|---|---|
| `mapped` + v1도 탐지 | 정상 (True Positive) | 수정안 생성 |
| `mapped` + v1은 미탐지 | **v1의 누락** (False Negative) | 규칙 민감도 재검토 |
| `unmapped` | **v1에 규칙 자체가 없음** | 신규 규칙 후보 |

세 번째 줄이 곧 로드맵이 된다.

### 3-3. re-check — 재점검

**책임**: 반려된 소재의 랜딩페이지를 v1으로 다시 점검한다.

> 🔧 **구현에서 바뀐 부분** — 원안은 "기존 `/v1/check`를 그대로 호출한다"였다.
> 그렇게 하면 네트워크와 LLM이 끼어서 이 모듈을 테스트할 수 없고, 채점 결과가
> 실행할 때마다 달라진다. **점검기를 주입받는 구조**로 바꿨다.

```python
class PageChecker(Protocol):
    def __call__(self, *, url: str, ad_copy: str, headlines: list[str],
                 descriptions: list[str]) -> set[str]: ...

# 운영: v1 파이프라인을 꽂는다
# 테스트·재현: 저장된 HTML로 도는 make_offline_checker 를 꽂는다
outcomes = recheck_ad(ad, checker, ledger=unmapped)
```

오프라인 점검기는 **평가 하네스와 같은 계층**(`evalkit.runner.html_only_findings`)을
쓴다. 두 곳이 다른 판정을 내면 골든셋 숫자와 재현율 숫자를 비교할 수 없다.

**여기서 얻는 것**

```
Google이 지목한 사유를 v1도 찾았는가?
  ├─ 찾았다  → 수정안 생성으로 진행 (evidence가 이미 있음)
  └─ 못 찾았다 → 두 가지 경우로 갈린다
       ├─ 페이지가 그 사이 바뀌었다     → 스냅샷 비교로 판별
       └─ v1 규칙이 못 잡는 케이스다    → 규칙 개선 티켓 자동 생성
```

두 번째 갈래를 구분하려면 **제출 당시의 페이지 스냅샷**이 필요하다. v1의 `check-history`에 이미 저장 중이므로 재사용한다. 없으면 "판별 불가"로 기록하고 추측하지 않는다 — v1의 원칙 그대로.

### 3-4. remediator — 수정안 생성

**책임**: 무엇을 어떻게 고칠지 제시한다. **고치지는 않는다.**

rule id별로 결정적(deterministic) 전략을 먼저 적용하고, 그것으로 안 되는 것만 LLM에 넘긴다.

```python
STRATEGY: dict[str, Strategy] = {
    # 규칙 기반 — LLM 불필요
    "AD-HEADLINE-TOO-LONG":  TruncateHeadline(),      # 15자/30자 규칙
    "AD-PUNCT-REPEAT":       StripRepeatedPunct(),
    "AD-EMOJI":              StripEmoji(),
    "KR-CONSENT-MISSING":    SuggestConsentBlock(),   # 문안 템플릿 제시

    # LLM 기반 — 판단이 필요한 것
    "MIS-CLICKBAIT":         RewriteWithLLM(tone="사실 기반"),
    "MIS-EXAGGERATION":      RewriteWithLLM(tone="수치 근거 명시"),

    # 자동 수정 불가 — 사람에게 넘김
    "ABUSE-CLOAKING":        ManualOnly(
        reason="클로킹은 코드/서버 설정 문제다. 문구 수정으로 해결되지 않는다."),
    "ABUSE-PARAM-CLOAKING":  ManualOnly(reason="위와 동일"),
    "DEST-UNREACHABLE":      ManualOnly(reason="인프라 문제"),
}
```

**설계 판단 — 자동 수정의 경계**

| 구분 | 자동 수정 | 근거 |
|---|---|---|
| 길이·기호·이모지 | ⭕ | 규칙이 결정적이고 의미가 안 바뀐다 |
| 문구 어조 | △ LLM 제안 + 사람 승인 | 의미가 바뀔 수 있다 |
| 랜딩페이지 내용 | ❌ | 우리 시스템이 고객 사이트를 고칠 권한이 없다 |
| 클로킹·서버 분기 | ❌ | 의도적 행위일 가능성. 자동 "수정"은 은폐가 된다 |

마지막 줄이 중요하다. **클로킹을 자동으로 없애주는 기능은 만들지 않는다.** 그건 위반을 감추는 도구다. 사유를 보여주고 사람이 판단하게 한다.

**모든 수정안에 evidence를 붙인다**

v1의 `verify_evidence`(증거 역추적)를 그대로 재사용한다.

```
수정안:  "업계 1위" → "2025년 OO조사 기준 점유율 1위"
근거:    MIS-EXAGGERATION / 본문 342자 위치
         "업계 1위 서비스" (rule, 신뢰도 1.0)
출처:    Google policy_topic_entry
         topic=UNSUBSTANTIATED_CLAIM
```

근거 없는 수정안은 만들지 않는다. LLM이 근거를 지어내면 `verify_evidence`가 걸러낸다.

### 3-5. approval gate — 사람 승인

**책임**: 자동 실행을 막는다.

```
┌─ 반려 사유 ────────────────────────────────┐
│ CLOAKING (PROHIBITED)                      │
│ Google 근거: 크롤러와 사용자에게 다른 내용  │
├─ 우리 시스템의 재점검 ─────────────────────┤
│ ✅ ABUSE-PARAM-CLOAKING (block) 로 탐지됨   │
│    gclid 부착 시 본문 유사도 0.31          │
│    대조군 자기유사도 0.97                   │
├─ 수정안 ───────────────────────────────────┤
│ ❌ 자동 수정 불가 — 서버 분기 코드 문제      │
│    랜딩페이지의 파라미터 분기 로직을         │
│    제거해야 합니다. (위치: main.js:142)     │
├────────────────────────────────────────────┤
│  [ 확인함 ]  [ 재제출 ]  [ 무시 ]            │
└────────────────────────────────────────────┘
```

**설계 판단**

- **자동 승인 옵션을 제공하지 않는다.** 설정으로도 켤 수 없다.
- 길이·기호 같은 결정적 수정도 사람이 누른다. 광고 문구는 브랜드 자산이다.
- 승인 이력을 기록한다 — 누가 언제 무엇을 승인했는지. 감사 대상이다.

### 3-6. resubmitter — 재제출

**책임**: 승인된 수정을 반영하고 심사에 다시 올린다.

```python
MAX_RESUBMIT_PER_AD = 3        # 같은 소재 재제출 상한
COOLDOWN_HOURS      = 24       # 재제출 간 최소 간격
MAX_RESUBMIT_PER_DAY = 20      # 계정 전체 일일 상한
```

**왜 상한을 두는가**

무제한 재제출은 세 가지 문제를 만든다.

1. **심사 시스템에 대한 부하** — 대량 재제출은 그 자체로 어뷰징 신호
2. **우회 시도로 해석될 수 있음** — "반려될 때까지 조금씩 바꿔 넣기"는 시스템 우회다
3. **근본 원인을 가린다** — 3번 고쳐서 안 되면 문구 문제가 아니라 사업/페이지 문제다

3회 초과 시 **자동으로 중단하고 사람에게 에스컬레이션**한다. 이 상한은 설정으로 낮출 수는 있어도 높일 수는 없게 한다.

⚠️ **미확인 — 구현 전 조사 필요**
- 소재 수정 후 재심사가 자동 진입하는지, 별도 요청이 필요한지
- **정책 이의제기(appeal)를 API로 제출할 수 있는지** — 확인한 범위에서는 주로 UI 기능으로 문서화되어 있다. API 경로가 없다면 이 시스템은 "수정 후 재등록"까지만 하고, 이의제기는 사람이 UI에서 하도록 안내한다.

### 3-7. ledger — 플라이휠 원장

**책임**: 무엇을 고쳤더니 무엇이 됐는지를 남긴다.

```jsonc
{
  "event_id": "rem_01JQ...",
  "ts": "2026-09-12T10:30:00Z",
  "ad_id": "123456789",
  "cycle": 1,

  "google": {
    "topic": "UNSUBSTANTIATED_CLAIM",
    "type": "LIMITED",
    "evidence": "업계 1위 서비스"
  },
  "ours": {
    "mapping_status": "mapped",
    "rule_ids": ["MIS-EXAGGERATION"],
    "detected": true,                  // v1도 잡았는가
    "severity": "warn"
  },
  "remediation": {
    "strategy": "RewriteWithLLM",
    "before": "업계 1위 서비스",
    "after": "2025년 OO조사 기준 점유율 1위",
    "approved_by": "ween",
    "approved_at": "2026-09-12T11:02:00Z"
  },
  "outcome": {
    "resubmitted_at": "2026-09-12T11:03:00Z",
    "result": "APPROVED",             // APPROVED | DISAPPROVED | PENDING
    "observed_at": "2026-09-13T09:15:00Z",
    "latency_hours": 22.2
  }
}
```

**이 원장에서 뽑는 지표**

| 지표 | 계산 | 쓰임 |
|---|---|---|
| **규칙 재현율** | `detected=true` / 전체 mapped | v1이 얼마나 놓치는가 |
| **미매핑 비율** | `unmapped` / 전체 | v1에 없는 규칙이 얼마나 되는가 |
| **전략 승률** | strategy별 `APPROVED` 비율 | 어떤 수정이 실제로 통하는가 |
| **평균 복구 시간** | `latency_hours` 중앙값 | 제품 가치의 핵심 숫자 |
| **사이클 분포** | `cycle` 히스토그램 | 한 번에 고쳐지는 비율 |

**여기가 플라이휠이 도는 지점이다.** 전략 승률이 낮은 rule은 전략을 바꾸고, 재현율이 낮은 rule은 v1 규칙을 손본다. 미매핑이 쌓이면 신규 규칙을 만든다.

## 6. 테스트 전략

v1의 방식(실제 로컬 서버로 재현 → 수정 → 옛 코드에서 실패하는 테스트로 증명)을 그대로 따른다.

| 계층 | 방법 | 비고 |
|---|---|---|
| Ads API 연동 | **테스트 계정**으로 실제 호출 | Google Ads는 테스트 MCC 계정을 제공. 실계정으로 개발하지 않는다 |
| normalizer | 고정 topic 문자열 → 기대 rule id | 순수 함수. 테스트 쉬움 |
| unmapped 처리 | 알 수 없는 topic 주입 | **격리되고 버려지지 않는지** 확인 |
| re-check | v1 테스트 픽스처 재사용 | 네트워크 타지 않게 |
| remediator | 전략별 before/after 스냅샷 | LLM 전략은 evidence 검증 통과 여부만 확인 |
| 안전장치 | **상한 초과 시 실제로 멈추는지** | 가장 중요. 이게 깨지면 시스템이 위험해진다 |
| 원장 | 지표 계산의 정확성 | 재현율·승률 산식 검증 |

**특히 검증해야 할 것**

```python
def test_resubmit_stops_at_limit():
    """3회를 넘기면 재제출이 아니라 에스컬레이션이 나와야 한다."""

def test_suspended_account_halts_everything():
    """계정이 정지되면 소재 수정 시도 자체를 하지 않아야 한다."""

def test_cloaking_never_auto_fixed():
    """클로킹 사유에 자동 수정 전략이 붙지 않아야 한다."""

def test_unmapped_topic_is_recorded_not_dropped():
    """모르는 사유가 조용히 사라지지 않아야 한다."""
```

## 7. 구현 순서

각 단계가 **그 자체로 동작하는 것**이 되도록 쪼갠다.

| 단계 | 내용 | 기간 | 완료 기준 | 상태 |
|---|---|---|---|---|
| **0** | 🚨 **테스트 계정에서 정책 심사가 도는지 확인** | 30분 | 일부러 위반 소재를 하나 올려 `approval_status`가 채워지는지 | ⬜ **토큰 필요** |
| **1** | Ads API 읽기 전용 연동 + 반려 목록 조회 | 2일 | 테스트 계정의 반려 소재를 JSON으로 덤프 | ⚠️ 어댑터 경계까지 |
| **2** | normalizer + unmapped 원장 | 1일 | 매핑률 리포트 출력 | ✅ |
| **3** | re-check 연동 + 재현율 측정 | 2일 | **"v1이 몇 %를 잡았는가" 숫자가 나옴** | ✅ |
| **4** | 원장 + 지표 대시보드 | 2일 | 리포트 생성 (`--md`) | ✅ CLI까지 |
| **5** | remediator (규칙 기반만) | 2일 | 길이·기호·이모지 수정안 생성 | ⬜ |
| **6** | 승인 UI | 2일 | 수정안 검토·승인 화면 | ⬜ |
| **7** | resubmitter + 안전장치 | 3일 | 상한·쿨다운 테스트 통과 | ⚠️ 안전장치만 |
| **8** | remediator (LLM) | 2일 | evidence 검증 통과하는 제안만 | ⬜ |

**0단계를 새로 넣었다.** §8-1에 적은 대로 테스트 계정에서 심사가 도는지가 불확실하고, **여기 결과에 따라 1단계 이후의 검증 방법이 갈린다.** 토큰을 받으면 가장 먼저 할 일이다.

- 심사가 돈다 → 설계서대로 테스트 계정으로 검증
- 심사가 안 돈다 → `watcher`/`normalizer`를 실데이터로 검증할 방법이 없다. Basic 액세스 + 실계정 + 실제 예산이 필요해진다

**3단계에서 이미 값이 나온다.** 재제출을 구현하지 않아도 *"우리 사전 점검이 실제 반려의 몇 %를 예측했는가"* 라는 숫자가 손에 들어온다. 포트폴리오 관점에서는 여기까지만 해도 충분하다.

**1~4단계까지 구현했다.** 다만 1단계는 **어댑터 경계와 `FakeAdsClient`까지**이고, 실제 `GoogleAdsClient`는 0단계를 통과한 뒤에 채운다(위 "달라진 점 ③").

## 8. 한계와 미검증 사항

정직하게 적는다. v1 README의 「한계」 절과 같은 성격.

### 8-1. 확인하지 못한 것

- **이의제기 API 지원 여부** — 정책 재심사·이의제기가 API로 가능한지 확인하지 못했다. UI 전용이라면 [6] 단계의 범위가 "수정 후 재등록"으로 축소된다.
- **policy_topic 전체 목록** — Google이 사용하는 topic 문자열의 완전한 목록은 공개 명세가 없다. 매핑 테이블은 **관찰하면서 채워나가는 수밖에 없다.** 그래서 `TOPIC_TO_RULES`는 확인된 것만 담고, 나머지는 `UnmappedLedger`가 모은다.
- **API 쿼터** — 폴링 주기와 계정 수에 따른 쿼터 소모량을 계산하지 않았다.
- **필드명·enum 값** — 이 문서의 API 필드는 설계 논의용이며, 사용할 API 버전에서 직접 확인해야 한다. 구현한 픽스처에도 같은 경고를 박아 두었고(`_note`), 테스트가 그 경고의 존재를 확인한다.
- 🚨 **테스트 계정에서 정책 심사가 실제로 도는지** — 가장 큰 미확인 사항이다. §6이 "테스트 계정으로 검증한다"를 전제로 하는데, 공식 문서는 테스트 계정이 *"광고를 게재하지 않고 취소된 계정으로 표시된다"* 고 적고 있다. 심사 파이프라인이 그런 계정에서도 `policy_summary`를 채워 주는지 문서에서 답을 찾지 못했다. **안 돈다면 §6의 전제가 무너지고, Basic 액세스 + 실계정 + 실제 예산이 필요해진다.** → §7의 0단계로 편입했다.

### 8-2. 구조적 한계

- **랜딩페이지를 고칠 수 없다.** 반려 사유의 상당수는 페이지 쪽 문제인데, 이 시스템은 제안만 한다. 실제 수정은 고객이 한다.
- **인과를 증명하지 못한다.** "수정했더니 승인됐다"는 상관관계다. Google 심사에는 사람이 개입하고, 같은 소재도 시점에 따라 판정이 달라질 수 있다. 전략 승률은 **경향**이지 인과가 아니다. 원장에 이 점을 명시한다.
- **소규모 데이터 문제.** 전략 승률이 의미를 가지려면 전략당 최소 수십 건이 필요하다. 초기에는 숫자를 신뢰하면 안 된다. **표본 수를 항상 같이 표시한다.**
- **계정 정지는 다루지 않는다.** 소재 반려와 계정 정지는 다른 문제다. 후자는 감지하고 멈추는 것까지만 한다.

### 8-3. 하지 않기로 한 것 (재확인)

계정 재생성, 도메인 교체를 통한 재시도, 사람 승인 없는 대량 재제출. 전부 시스템 우회에 해당하며, 이 시스템의 설계 목적과 정면으로 충돌한다.

## 9. 이 프로젝트가 가지는 의미

### 9-1. v1의 빈 곳을 정확히 메운다

v1은 "예측"만 하고 채점표가 없었다. v2는 **정답지를 가져와 채점한다.** 이것 하나로 `adpolicy-precheck`는 "만들어본 도구"에서 "측정된 시스템"이 된다.

### 9-2. 면접에서 쓸 수 있는 형태

> "광고 소재가 반려되면 Google Ads API로 사유를 수집해 우리 규칙 체계에 매핑하고, 해당 랜딩페이지를 재점검해 우리 사전 점검이 그 사유를 예측했는지 채점합니다. 매핑되지 않는 사유는 버리지 않고 격리해서 규칙 누락 목록으로 쌓습니다. 수정안은 증거 역추적을 통과한 것만 제시하고, 자동 실행은 하지 않습니다 — 재제출 3회 상한과 사람 승인 게이트를 우회할 수 없게 설계했습니다."

여기에 들어 있는 것:
- 외부 API 연동 설계 (**스텝에이아이**: "외부 API 연동 시 timeout·재시도·폴백을 스스로 설계해 본 경험")
- 평가 체계 (**브레인크루**: "자체 evaluation set", **케이존**: "evaluation, guardrail")
- 광고 도메인 (**버즈빌**)
- 자기 개선 루프 (**에어스메디컬**: Flywheel 엔진)

하나의 프로젝트가 네 공고의 요건을 동시에 건드린다.

### 9-3. 앞서 논의한 「평가 하네스」와의 관계

평가 하네스는 **골든셋(우리가 라벨링)** 기반이고, v2는 **실제 판정(Google이 라벨링)** 기반이다. 둘은 경쟁하지 않고 보완한다.

| | 평가 하네스 | v2 원장 |
|---|---|---|
| 라벨 출처 | 직접 라벨링 | Google 실제 판정 |
| 규모 | 30~50건 (고정) | 계속 증가 |
| 즉시성 | 오늘 만들면 오늘 숫자 | 실계정 운영이 필요 |
| 신뢰도 | 라벨이 주관적일 수 있음 | 정답에 가까움 |

**평가 하네스를 먼저 만드는 게 맞다.** 실계정 없이 오늘 숫자가 나오고, v2의 재현율 측정 코드를 그대로 재사용할 수 있다.

초판에 "토큰 승인에 시간이 걸리니 미리 신청해두라"고 적었는데 **틀렸다.** 2026년 9월 9일부터 절차가 바뀌었다.

| | 옛 절차 | 현재 |
|---|---|---|
| 신청 경로 | Ads 매니저 계정 → API Center | **Google Cloud Console 직접** |

액세스 레벨은 셋이다.

| 레벨 | 호출 가능 | 일일 한도 | 취득 |
|---|---|---|---|
| **Test** (기본) | 테스트 계정만 | 15,000 ops | **Cloud 프로젝트에서 API 활성화만** |
| Basic | 테스트 + 실계정 | 15,000 ops | 브랜드 인증 후 자동 심사 — 수 분 |
| Standard | 테스트 + 실계정 | 무제한 | Basic 보유 + 수동 감사, 통상 10영업일 |

**대기할 필요가 없다.** 공식 문서가 테스트 계정은 *"API 접근 승인이 필요하지 않으며, 신청이 심사·승인되기 전에도 즉시 실험을 시작할 수 있다"* 고 적고 있다.

다만 테스트 계정에는 제약이 따른다 — 별도 테스트 매니저 계정이 루트로 필요하고(프로덕션과 다른 Google 계정), **광고가 노출되지 않으며**, 노출·전환·비용 데이터가 비어 있고, 계층당 50개까지, 1년 미사용 시 자동 삭제된다. 두 번째 항목이 §8-1의 0단계 불확실성을 만든 원인이다.
