# 설계서 — adpolicy-precheck

## 1. 문제 정의

광고 심사 반려는 **사후에 알게 된다.** 집행을 걸고 하루 이틀 기다린 뒤에야 "정책 위반"이라는 통보를 받고, 무엇이 문제였는지는 대개 모호하게 적혀 있다. 반복되면 계정 신뢰도까지 깎인다.

이 도구는 그 루프를 앞으로 당긴다. **집행 전에, 근거와 함께, 무엇을 고쳐야 하는지** 알려주는 것이 목표다.

## 2. 왜 LLM만으로는 안 되는가

초기 구현은 LLM에게 페이지와 문구를 통째로 주고 판단을 맡겼다. 두 가지가 무너졌다.

**환각** — 모델이 페이지에 없는 문장을 근거로 인용했다. "'완치 보장'이라고 적혀 있습니다"라고 하는데 실제로는 그런 문구가 없다. 사용자는 있지도 않은 문제를 고치려 시간을 쓴다.

**비결정성** — 같은 페이지를 두 번 검사하면 다른 결과가 나왔다. 수정 전후를 비교할 수 없으니 도구로서 쓸모가 없다.

두 문제 모두 **모델을 더 크게 하거나 프롬프트를 다듬어서** 풀려고 하면 한계가 있다. 구조로 풀어야 한다.

## 3. 해결 — 계층 분리

```
입력(URL + 문구[제목·설명])
      │
      ├───────────────────────────────────┐
      ▼                                   ▼
  ┌─────────────┐                   ┌─────────────┐
  │  fetcher    │                   │  adcopy     │  글자 수·기호·반복
  │  SSRF 홉마다 │                   │  문구만 본다 │  페이지가 안 열려도 판정 가능
  └─────────────┘                   └─────────────┘
      │  실패는 예외가 아니라 fetch_error 상태
      ▼
  ┌───────────────────────────────────────┐
  │  cloaking.probe_profiles / probe_params│
  │  같은 URL을 두 축으로 가져온다          │
  │   · 누가 보나 — 데스크톱 / 모바일 / 봇  │
  │   · 어떻게 왔나 — 파라미터 없음(대조군) │

      ▼

  │  vision     │  이미지 수집 → OCR → ocr_text
  └─────────────┘  (선택) VLM으로 이미지 자체 판정
      │
      ├──────────────────────┐
      ▼                      ▼
  ┌─────────────┐      ┌─────────────┐
  │  rules      │      │  analyzer   │
  │  결정적      │      │  LLM + CoT  │
  │  재현성 100% │      │             │
  └─────────────┘      └──────┬──────┘
      │  데스크톱 + 모바일           │
      │  (§4-14)                    ▼
      │                      ┌─────────────┐
      │                      │ verify_     │  ← 근거가 원문에 없으면 폐기
      │                      │ evidence    │
      │                      └──────┬──────┘
      │                             │
      └───────┬─────────────────────┘
              ▼
        ┌─────────────┐
        │  scoring    │  merge → score → verdict + account_risk (§4-11)
        └─────────────┘  전부 코드가 계산
              │
              ▼
        ┌─────────────┐
        │  history    │  본문 지문을 장부에 남긴다 → 다음 점검 때 비교 (§4-13)
        └─────────────┘
              │
   ┌──────────┴───────────┐         이 위까지가 "판정"이고,
   ▼                      ▼         아래는 **표면**과 **측정**이다 (§9, §10)
┌────────┐          ┌────────────┐
│ main   │ HTTP API │ mcp_server │ MCP — 에이전트가 부르는 표면 (읽기 전용)
└────────┘          └────────────┘
```

**원칙: 판단은 LLM에게, 사실 확인은 코드에게.**

- 코드가 확정할 수 있는 것(개인정보처리방침 링크가 있는가, HTTP인가, 가격 표기가 있는가)은 **LLM에게 묻지 않는다.**
- LLM은 코드가 못 하는 것만 한다 — 맥락상 과장인가, 오해를 유발하는가.
- LLM의 출력은 **반드시 코드의 검증을 거친다.**

## 4. 주요 설계 결정

### 4-1. 왜 evidence를 필수로 두었는가

Finding 스키마에 `evidence`를 두고, LLM 경로에서는 검증을 통과하지 못하면 폐기한다.

부수 효과가 크다. 사용자가 "왜 이게 문제냐"고 물었을 때 **페이지의 어느 문장 때문인지** 바로 보여줄 수 있다. 근거 없는 지적은 고칠 수도 없다.

### 4-2. 왜 공백을 제거하고 비교하는가

초기 구현은 공백을 하나로 줄이기만 했다(`\s+` → `" "`). 그랬더니 모델이 `100 % 보장`으로 인용했을 때 원문 `100% 보장`과 매칭에 실패해, **맞는 지적이 폐기**됐다.

한국어는 띄어쓰기 변형이 특히 잦다. 공백을 전부 제거하면 재포맷은 흡수하면서 문자 순서는 보존하므로, 글자가 다른 진짜 환각은 여전히 걸러진다. 이 결정은 테스트로 고정돼 있다.

```python
def test_verify_evidence_tolerates_whitespace_difference():
    assert verify_evidence("100 %  보장", "효과 100% 보장 합니다")

def test_verify_evidence_rejects_hallucination():
    assert not verify_evidence("무조건 완치됩니다", "저희는 효과 100% 보장 합니다")
```

### 4-3. 왜 부재 감지를 조건부로 하는가

"가격이 없다"를 무조건 지적하면 회사 소개 페이지에서 오탐이 난다. 그래서 **구매 유도 문구가 있을 때만** `MIS-DISHONEST-PRICING`을 올린다. 마찬가지로 `DATA-NO-PRIVACY-POLICY`는 개인정보를 수집하는 폼이 있을 때만 판정한다.

오탐이 몇 번 나면 사용자는 도구 전체를 믿지 않는다. 놓치는 것보다 잘못 지적하는 쪽이 더 비싸다.

### 4-4. 왜 점수를 코드가 계산하는가

LLM에게 "몇 점이냐"고 물으면 같은 findings에도 매번 다른 점수가 나온다. 사용자는 **수정 전후를 비교**하려고 점수를 본다. 그러니 findings가 같으면 점수도 반드시 같아야 한다.

RULE과 LLM 출처에 다른 가중치(1.0 / 0.7)를 둔 것도 같은 맥락이다. 확실한 것과 추정을 같은 무게로 다루면 안 된다.

### 4-5. 왜 LLM 실패가 전체 실패가 아닌가

LLM 서버가 죽어도 결정적 룰셋 결과는 유효하다. 그래서 `analyze()`는 예외를 던지지 않고 `(findings, stats, analysis, error)`를 돌려주며, API는 룰셋 결과에 `llm_note`로 사유를 붙여 응답한다.

조용히 빈 결과를 주는 것이 최악이다. "LLM 서버에 연결할 수 없습니다"라고 말하고, **할 수 있는 만큼은 해 준다.**

### 4-6. 이미지에서 읽은 글자를 어디에 합치는가

이미지 기능을 넣으면서 가장 조심한 지점이다. 합치는 위치 하나로 결과가 갈린다.

| | 무엇이 들어가나 | 누가 보나 |
|---|---|---|
| `combined_text` | 페이지 텍스트만 | 결정적 룰 |
| `verification_text` | 페이지 + OCR 텍스트 | `verify_evidence` |

`combined_text`에 OCR을 넣으면 본문 룰이 배너 문구까지 잡아 `source=rule`로
보고하고, **어느 이미지에서 나왔는지가 사라진다.** 반대로 `verification_text`에
넣지 않으면 배너 문구를 인용한 모델 판단을 대조할 수 없어 환각이 통과한다.
양방향 모두 테스트로 고정했다.

분량을 재는 판정(`DEST-INSUFFICIENT-CONTENT`)만은 예외로 OCR 글자를 함께 센다.
거기서는 근거의 **출처**가 아니라 **양**이 쟁점이기 때문이다. 본문이 짧지만
이미지에 내용이 있으면 `DEST-IMAGE-ONLY-CONTENT`(info)로 따로 알린다.

### 4-7. 역검증이 불가능한 판단을 어떻게 다루는가

이미지 **자체**에 대한 VLM 판단(비포·애프터 사진, 노출 등)은 인용할 문구가
없어 `verify_evidence`를 적용할 수 없다. 이 저장소의 전제가 하나 무너지는
지점이라, 숨기지 않고 구조에 드러냈다.

| source | 가중치 | 역검증 |
|---|---|---|
| `rule` | 1.0 | 불필요 (코드가 판정) |
| `ocr` | 0.85 | OCR 텍스트와 대조 가능 |
| `llm` | 0.7 | 페이지 텍스트와 대조 가능 |
| `vlm` | 0.5 | **불가능** — 사람이 확인 |

`vlm`은 추가로 `block`을 `warn`으로 낮추고, 판정한 `image_url`을 반드시
반환하며, 우리가 받지 않은 이미지나 텍스트 룰이 담당하는 코드를 올리면 폐기한다.

### 4-8. 국내 법령 항목을 왜 분리했는가

`KR-NO-CONSENT`·`KR-INCOMPLETE-CONSENT`는 Google 정책이 아니라 개인정보 보호법
기준이다. 카탈로그의 다른 항목이 공식 분류에 매핑돼 있는데 여기에 섞으면
"심사 반려 사유인가, 법 위반인가"가 흐려진다. `category="국내 법령"`과 법령
`source`로 분리하고 테스트로 고정했다.

개인정보처리방침과 수집·이용 동의는 서로를 대신하지 못한다 — 방침은 상시
공개하는 문서고, 동의는 수집 시점의 행위다. 그래서 따로 판정한다.

### 4-9. SSRF 방어

사용자가 임의 URL을 넣는 서비스라 내부망 스캔 통로가 되기 쉽다. 사설 IP·
루프백·링크로컬·CGNAT·멀티캐스트를 거부하고, http/https 외 스킴을 막는다.

**가드를 최초 URL에만 거는 것으로는 부족하다.** `follow_redirects=True`로
맡기면 302 한 번에 `127.0.0.1`이든 `169.254.169.254`든 그대로 읽힌다.
그래서 리디렉션을 직접 돌며 홉마다 다시 검사한다(`safe_get`). 페이지·클로킹
3프로필·파라미터 4조합·재확인·이미지·robots.txt가 전부 이 함수를 지난다.
이름 풀이는 스레드로 넘긴다(`assert_safe_url_async`) — 동시에 여러 곳을 가져오는
구조라 블로킹 DNS 하나가 서버 전체를 세운다.

### 4-10. 자원 상한 — 공격자가 응답을 통제한다

사용자가 임의 URL을 넣으면 서버가 그 페이지와 **거기 실린 모든 이미지**를
가져온다. 즉 응답 내용·크기·리디렉션을 전부 공격자가 정한다.

| 위협 | 막는 곳 |
|---|---|
| 리디렉션으로 내부망 접근 | `safe_get`이 **홉마다** 가드를 다시 건다 |
| 압축 폭탄 | 스트리밍으로 받으며 세다가 상한에서 끊는다 |
| 픽셀 폭탄 | 확대 전후로 픽셀 수를 검사 |
| 이미지 물량 | 장수·장당·**총량** 상한 |
| CPU 독점 | OCR은 스레드로 분리 + 세마포어 |
| 전체 지연 | `/v1/check`에 데드라인(504) |

`resp.content`를 받아 뒤에서 자르는 방식은 이미 다 풀린 뒤라 의미가 없다.
가드를 최초 URL에만 거는 것도 302 한 번이면 무력화된다. 둘 다 실제로 뚫렸던
경로이고, `tests/test_security.py`가 지킨다.

### 4-11. 반려와 계정 정지를 왜 다른 축으로 두었는가

광고 하나가 반려되는 것과 계정이 **영구 정지**되는 것은 광고주에게 완전히 다른
사건이다. 그런데 `severity`(block/warn/info) 하나로는 그 차이가 표현되지 않는다.
반려 20건이 정지 1건보다 점수를 많이 깎는 일이 생긴다.

그래서 `Enforcement`를 두 번째 축으로 분리했다. 등급은 내 판단이 아니라 **정책
문서에 박혀 있는 정형 문장**으로 갈랐다.

| 등급 | 문서의 문장 |
|---|---|
| `suspend` | "사전 경고 없이 즉시 해당 Google Ads 계정을 정지하며 …" |
| `disapprove` | "이 정책을 위반해도 사전 경고 없이 바로 계정이 정지되지는 않습니다." |

**VLM이 이미지를 보고 한 추측은 절대 정지급으로 보고하지 않는다.** 인용할 문구
하나 없는 모델 판단을 근거로 "계정이 정지됩니다"라고 말할 수는 없다.

### 4-12. 대조군 — 무엇과 비교할 것인가

클로킹 판정의 핵심은 "다르다"가 아니라 **"무엇 때문에 다른가"**다. 배너가
돌아가거나 추천 상품이 섞이는 페이지는 **같은 주소를 두 번 불러도** 본문이
달라진다. 그 차이를 gclid나 User-Agent 탓으로 돌리면 멀쩡한 쇼핑몰이 계정 정지
위험으로 뜬다.

그래서 아무것도 바꾸지 않고 한 번 더 부른다. 이것이 **잡음 기준선**이다.

```
차이가 잡음보다 뚜렷할 때만 판정한다.
잡음이 85%보다 크면(= 페이지가 스스로 많이 변하면) 판정을 포기하고 사유를 남긴다.
```

"문제없음"과 "판정 못 함"은 다르다. 후자를 조용히 넘기면 사용자는 확인된 줄 안다.

두 가지를 더 지킨다.

- **응답을 못 받은 것과 다른 내용이 온 것을 구분한다.** 국내 호스팅은 요청이
  몰리면 "잠시 후 다시 시도" 안내를 **200으로** 준다. 26자짜리 안내 페이지를
  본문 비교에 넣으면 유사도 0.02가 나오고 정지급으로 보고된다. 실제로 그랬다.
- **정지급 판정은 한 번의 관찰로 확정하지 않는다.** 지적을 올리기 전에 대조군과
  문제의 변형을 **사이를 두고 하나씩** 다시 부른다. 몰아 보내는 것 자체가
  원인일 수 있으므로 이번에는 순차로 부르고, 두 응답을 서로 비교한다.

### 4-13. 한 번의 점검으로 증명할 수 없는 것

심사만 통과시키고 갈아끼우는 수법은 **시점이 다른 두 번의 점검**으로만 드러난다.
그래서 본문 지문(제목 + 본문 + OCR의 해시)을 응답에 싣고 장부에 남긴다.

다만 "바뀌었다"는 **사실이지 위반이 아니다.** 오타를 고쳤다고 계정 정지 위험이
뜨면 안 된다. 그래서 비교 정보는 항상 보여주되, 지적으로 올릴지는 호출자가
`compare_with_last`로 정한다. 이미 심사를 통과한 페이지일 때만 켜는 스위치다.

같은 원칙이 다른 곳에도 걸린다. **증명된 것까지만 말한다.**

| 탐지 | 증명되는 것 | 등급 |
|---|---|---|
| 서버가 파라미터로 분기 | 실제로 다른 본문이 왔다 | `block` |
| 스크립트가 파라미터를 읽고 화면을 바꿈 | **구조가 있다**는 것까지 | `warn` |
| 본문을 서버에서 받아 채우는 구조 | 바꿔치기할 수 있다는 것까지 | `warn` |

가운데 항목이 `warn`인 이유는 서버 응답이 어느 파라미터로 불러도 같기 때문이다.
실제로 다른 내용이 나가는지는 브라우저에서 확인해야 하고, 그 안내를 `fix`에 넣었다.

### 4-14. 이미 가진 데이터를 쓴다 — 모바일 스냅샷

클로킹 비교를 위해 모바일 프로필을 **이미 받아 두고** 룰셋은 데스크톱만 보고
있었다. 데스크톱 푸터에만 가격·사업자 정보가 있는 구성은 국내에서 아주 흔한데
그게 전부 통과했다. 같은 스냅샷에 룰셋을 한 번 더 돌리는 데 추가 네트워크
비용은 0이다.

데스크톱에서 이미 나온 코드는 올리지 않고, 새로 나온 것에는 `[모바일]`을 붙인다.
어느 화면의 문제인지 밝히지 않으면 사용자가 데스크톱을 열어보고 "없는데?" 한다.

### 4-15. 문구 점검은 왜 페이지와 분리했는가

`adcopy`는 랜딩페이지를 보지 않는다. 광고 텍스트만 보므로 **페이지가 안 열려도
판정된다.** 그리고 이 축은 전부 결정적이다 — 이 저장소에서 "고치면 반드시
통과한다"고 말할 수 있는 거의 유일한 부분이다.

가장 중요한 사실 하나는 문서에서 왔다. "한국어, 일본어, 중국어와 같은 2바이트
언어의 경우 문자 한 개를 두 자로 계산해 한도를 적용합니다." 즉 **영문 30자인
제목이 한글로는 15자**다.

길이는 제목·설명을 나눠서 준 경우에만 판정한다. 뭉뚱그린 한 덩어리로는 어느
필드인지 알 수 없고, 모르면서 "30자를 넘었다"고 하면 거짓이 된다.

**문서에 없는 규칙은 넣지 않았다.** "여기를 클릭" 같은 일반적 유도 문구는 흔히
금지 항목으로 이야기되지만 편집 기준 문서(한국어·영문)에 그런 조항이 없어
넣지 않았다. 이모지도 문서가 이름으로 지목하지 않아 '기호 남용'으로 묶고 그
사실을 설명에 적었다. 없는 근거로 지적하면 나머지 판정까지 함께 의심받는다.

## 9. 측정 계층 — 예측을 채점한다

§3까지가 "판정"이라면 이 절은 **"판정이 맞았는지 재는 장치"** 다. 예측만 하고 채점표가 없으면 어디를 고쳐야 할지 알 수 없다.

측정 장치는 둘이고, **라벨의 출처가 다르다.** 그래서 경쟁하지 않고 보완한다.

| | 우리가 만든 라벨 | Google의 실제 판정 |
|---|---|---|
| 모듈 | `adpolicy/evalkit/` | `adpolicy/ads/` |
| 실행 | `python -m adpolicy.evalkit` | `python -m adpolicy.ads` |
| 데이터 | `api/eval/golden/` 24건 | 반려 사유 수집 (픽스처) |
| 지표 | 정밀도 · 재현율 · F1 (코드별) | **재현율** + 규칙 대응률 |
| 즉시성 | 오늘 바로 숫자가 나온다 | 실계정·토큰이 필요하다 |
| 한계 | 라벨이 주관적일 수 있다 | 표본이 쌓이는 데 시간이 걸린다 |

`ads/` 계층의 설계는 [설계서-v2-반려복구루프.md](설계서-v2-반려복구루프.md)에 따로 적었다. 이 문서에서는 **"왜 재는가"** 까지만 다룬다.

### 9-1. 왜 `expect`와 `forbid` 두 축인가

케이스에 "이 코드가 나와야 한다"만 적으면 **정상 페이지에서 엉뚱한 코드가 뜨는 오탐**을 잡을 수 없다. 실제로 정상 쇼핑몰이 계정 정지급 `ABUSE-CLOAKING`으로 보고된 사고가 있었다(§4-12의 대조군이 그 대응). 그 회귀 테스트가 골든셋에 들어 있다.

```
expect  반드시 나와야 하는 코드
forbid  나오면 오탐인 코드
```

### 9-2. 왜 채점 범위(scope)를 두는가

골든셋에 적지 않은 코드가 결과에 섞여 나왔을 때 전부 오탐으로 치면 라벨링 부담이 폭발한다 — 56개 코드를 케이스마다 전부 판정해야 한다. 그래서 **언급된 코드만 채점**하고, 나머지는 `unscored`로 따로 세어 리포트에 드러낸다.

> **라벨이 없는 것을 틀렸다고 말하지 않는다.** §4-7("역검증이 불가능한 판단")과 같은 태도다 — 모르는 것은 모른다고 적고, 숨기지는 않는다.

### 9-3. 왜 LLM을 빼고 재는가

하네스는 결정적 룰셋과 문구 편집 기준만 돌린다. 셋 때문이다.

1. **재현성** — LLM은 온도를 0으로 둬도 완전히 결정적이지 않다. 그러면 지표가 흔들린다
2. **비용** — 돌릴 때마다 토큰을 쓰면 자주 못 돌린다
3. **책임 분리** — 섞으면 "룰이 틀린 건지 모델이 틀린 건지" 구분이 사라진다

경계는 "네트워크를 쓰는가"가 아니라 **"재현 가능한가"** 다. 그래서 응답 HTML 하나로 끝나는 판정(숨긴 텍스트, 자동 리디렉션, 난독화 스크립트)은 포함하고, 여러 번 요청해야 아는 것(프로필 비교, 파라미터 프로브, robots.txt)은 제외한다.

### 9-4. 리포트가 반드시 보여야 하는 것

| | 이유 |
|---|---|
| **표본 수** | 3건짜리 F1 100%는 정보가 아니라 착시다. 모든 비율 옆에 붙인다 |
| **계정 정지급 오탐** | 반려 오탐과 무게가 다르다(§4-11). 맨 위에 따로 올린다 |
| **채점 안 된 코드** | "판단하지 않았다"와 "맞았다"는 다른 말이다 |

### 9-5. 하네스가 실제로 찾아낸 것

첫 실행에서 `MIS-CLICKBAIT`가 걸렸다. 카탈로그 설명은 *"클릭베이트 기법이나 **선정적 문구**"* 라고 적혀 있는데, 규칙은 허위 희소성(`단 N자리 남음`)만 구현하고 있었다. **카탈로그와 구현이 어긋나 있었던 것**이고, 사람이 읽어서는 눈치채기 어려운 종류의 불일치였다.

선정적 유인 갈래를 추가했고 신규 테스트 10건이 옛 패턴에서 실패한다. 넓힌 패턴이 오탐을 만들지 않는지는 트랩 케이스(`의사가 **알려주는**`)로 막았다.

## 10. MCP 표면 — 에이전트 앞에 세우는 게이트

### 10-1. 왜 필요한가

이 도구의 쓸모는 사람이 대시보드를 여는 쪽보다 **광고 문구를 생성하는 에이전트가 내보내기 전에 스스로 검증하는** 쪽에 있다. 그러려면 에이전트가 부를 수 있는 표면이 필요하다.

```
문구·랜딩 URL 생성 → precheck_ad → fail이면 findings[].fix 반영
      → 다시 precheck_ad → 통과하면 게재
```

### 10-2. 왜 읽기 전용인가

광고를 만들지도, 고치지도, 올리지도 않는다. **가드레일은 스스로 행위하지 않아야 신뢰할 수 있다.** `sql-guard-mcp`, `judge-mcp`와 같은 태도다.

이 원칙을 주석이 아니라 테스트로 강제했다 — 툴 **이름 수준**에서 쓰기 동사(`create`, `publish`, `submit`, `mutate`, `account` …)를 금지한다. 나중에 누가 무심코 툴을 추가해도 테스트가 먼저 깨진다.

### 10-3. 점검 실패를 통과로 위장하지 않는다

게이트가 조용히 통과시키면 게이트가 아니다. 점검이 끝나지 못하면 `error`를 돌려주고 **`verdict`를 아예 넣지 않는다** — 에이전트가 "verdict가 없으니 괜찮은가 보다"로 읽을 여지를 없애기 위해서다.

### 10-4. 왜 HTTP를 거치지 않는가

FastAPI 앱을 띄우고 그 위에 MCP를 얹으면 포트와 수명주기가 둘로 늘어난다. 엔진(`main._run_check`)이 이미 순수 async 함수라 직접 부르면 된다.

## 7. 클로킹 — 탐지는 하고, 수행은 하지 않는다

두 가지는 정반대 방향이다.

| | 클로킹 **수행** | 클로킹 **탐지** |
|---|---|---|
| 목적 | 심사를 속인다 | 사고를 미리 발견한다 |
| 필요한 것 | 크롤러 IP·UA 목록 | 프로필 간 응답 차이 |
| 결과 | 계정 영구 정지 | 정지를 예방 |

이 저장소는 **탐지만** 구현한다. 크롤러 IP 목록 수집이나 심사용/사용자용 페이지 분기는 범위 밖이다.

### 왜 크롤러 UA를 사칭하지 않는가

탐지에 필요가 없기 때문이다. 클로킹은 "클라이언트에 따라 다른 콘텐츠를 준다"는 행동이고, 그 행동은 **서로 구분되는 아무 프로필 둘**만 있으면 드러난다. Googlebot의 정확한 UA 문자열이 있어야만 잡히는 게 아니다.

오히려 정직하게 봇임을 밝힌 UA(`adpolicy-precheck/0.1`)가 더 좋은 프로브다. 사이트가 "봇으로 보이는 클라이언트"를 다르게 대우한다면 그게 정확히 우리가 찾는 행동이기 때문이다. 크롤러 사칭은 회색지대인 데다, 어차피 역방향 DNS로 검증되지 않아 신호로서도 약하다.

이 결정은 테스트로 고정돼 있다 — 누가 나중에 "Googlebot UA를 넣으면 탐지가 잘 되지 않을까" 하고 추가하면 CI가 막는다.

```python
def test_profiles_do_not_impersonate_search_crawlers():
    for ua in CLIENT_PROFILES.values():
        assert "googlebot" not in ua.lower()
        assert "adsbot" not in ua.lower()
```

### 판정 기준

본문 유사도(`difflib.SequenceMatcher`)로 프로필 쌍을 비교해 최저값을 쓴다.

| 유사도 | 판정 | 근거 |
|---|---|---|
| < 60% | block | 실질적으로 다른 페이지다 |
| 60~85% | warn | 반응형 차이로 보기엔 크다 |
| ≥ 85% | 정상 | 레이아웃·광고 슬롯 차이 수준 |

여기에 §4-12의 잡음 기준선이 함께 걸린다. 페이지가 스스로 변하는 만큼은 빼고 본다.

**`autojunk=False`가 반드시 필요하다.** `SequenceMatcher`의 기본값은 200자가
넘는 쪽에서 1% 넘게 나오는 요소를 '잡음'으로 빼는데, 상품 목록·후기처럼 같은
구조가 반복되는 페이지는 거의 모든 글자가 그 조건에 걸린다. 90% 닮은 두 페이지가
2%로 나왔고, 반복 구조가 있는 정상 쇼핑몰이 계정 정지급으로 보고됐다.

**브라우저에는 응답하는데 봇에만 실패**하는 경우는 유사도를 볼 것도 없이 걸린다.
WAF 봇 차단이 심사 크롤러를 막는 가장 흔한 사고 패턴이다. 다만 **왜 실패했는지는
구분한다** — 4xx는 사이트가 명시적으로 거부한 것이라 `block`, 타임아웃은 그냥 못
받은 것이라 `warn`이다. 봇만 실패하면 한 번 재시도한 뒤에 판정한다. 순간 네트워크
장애 한 번으로 정지급을 확정하는 것이 이 검사에서 가장 비싼 오탐이다.

`robots.txt`는 별도로 확인한다. AdsBot-Google이 전역 `User-agent: *`를 따르지
않는다는 점이 중요해서, AdsBot을 **명시적으로** Disallow한 경우만 판정한다.
전역 규칙만 보고 판정하면 오탐이 대량 발생한다. 경로 단위 `Disallow: /landing`도
판정하고(그러지 않으면 정작 잡아야 할 경우를 놓친다), `User-agent`가 여러 줄
연속으로 오는 그룹형 레코드도 처리한다.

### User-Agent만으로는 절반이다

위 표는 전부 **누가 보느냐**를 축으로 한다. 그런데 심사 크롤러는 광고를 클릭해서
오지 않으므로 도착 URL에 `gclid`가 붙지 않는다. "gclid가 있으면 진짜 페이지"로
짜두면 UA를 아무리 바꿔 비교해도 전부 얌전한 쪽만 보인다. 그래서 **어떻게
들어왔느냐**를 두 번째 축으로 둔다(§3 파이프라인).

찔러볼 때 쓰는 클릭 ID는 형식만 맞춘 **가짜 값**이다. 진짜를 쓰면 남의 광고
통계를 더럽힌다.

## 8. 정책 카탈로그의 출처

초기 버전은 내 지식에 의존해 항목 이름을 지었는데, 그건 심사에서 쓰이지 않는 용어라 실무자에게 의미가 없었다. 현재는 **Google Ads 공식 정책 문서의 분류와 명칭**을 따른다.

| 접두사 | 공식 분류 | 문서 |
|---|---|---|
| `DEST-` | 편집 및 기술 요건 → 방문 페이지 요건 | answer/6368661 |
| `MIS-` | 금지된 행위 → 허위 진술 | answer/6020955 |
| `ABUSE-` | 금지된 행위 → 광고 네트워크 악용 | answer/6020954 |
| `DATA-` | 금지된 행위 → 데이터 수집 및 사용 | answer/6008942 |
| `PROHIB-` / `RESTRICT-` | 금지·제한 콘텐츠 | answer/6008942 |
| `AD-` | 편집 및 기술 요건 → 광고소재(편집 기준) | answer/6021546 |
| `TT-` | TikTok 광고 정책 (별도 문서) | ads.tiktok.com |
| `KR-` | **Google 정책이 아니다** — 개인정보 보호법 (§4-8) | law.go.kr |

각 `PolicyItem`은 `official_name`과 `source` URL을 들고 있고, `GET /v1/policies`가 그대로 노출한다. 사용자가 "이게 왜 문제냐"고 물으면 **공식 문서로 바로 연결**된다.

공식 문서를 읽으면서 코드로 검사 가능한 항목을 추가로 발견했다.

- `DEST-NOT-CRAWLABLE` — robots.txt가 AdsBot 차단 (의도치 않은 사고가 많다)
- `MIS-UNCLEAR-RELEVANCE` — 광고 키워드가 페이지에서 확인되지 않음
- `MIS-UNAVAILABLE-OFFER` — 광고가 약속한 할인이 페이지에 없음
- `DEST-UNACCEPTABLE-URL` — IP 주소를 그대로 쓴 URL
- `DEST-AUTO-DOWNLOAD` — 진입 시 자동 다운로드

특히 뒤의 둘(관련성·혜택)은 **광고 문구와 페이지를 함께 봐야만** 잡히는 항목이라, 이 도구의 입력 구조(문구 + URL)가 제값을 하는 지점이다.
